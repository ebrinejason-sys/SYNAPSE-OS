## What "done" means here

This report distinguishes four different levels of confidence on purpose, because none of them substitute for the others:

- **Completed code** — implemented, reviewed in this repository, and exercised by at least one automated test run in this environment.
- **Isolated tests** — automated tests that ran and passed in this environment. Mock-based unit tests prove business-logic branches only; they cannot prove transaction atomicity, unique-constraint enforcement, RLS, or concurrency. DB-backed integration tests prove those, but only against whatever Postgres instance `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` point to in the environment that ran them — not against the production project unless that is explicitly stated.
- **Staging evidence** — a recorded run of the synthetic staging journey (see below) against an authorized, non-production Supabase project, with the resulting evidence artifact checked in or linked.
- **Production blockers** — concrete, named actions a human operator must still take before this can run against the production project. These are never described as "credential-only"; several are code/schema verification steps, not just secret provisioning.

## Completed code (this pass)

- **Multi-facility acceptance without overwriting the home tenant.** `apps/web/src/lib/tenant-scope.ts` (`isTenantScopeAllowed`) and `apps/web/src/lib/invite-scope.ts` (`canBindInviteToTenant`) previously rejected any profile whose `profiles.tenant_id` differed from the target facility, before ever checking `staff_scope_assignments` — the SQL acceptance functions had the identical bug. Both are fixed: a profile keeps its existing home tenant and gains additional facilities purely through `staff_scope_assignments` rows; access to a facility with neither a matching home tenant nor an active assignment is still denied. `apps/web/src/lib/tenant-isolation.test.ts` now asserts both directions explicitly (`allows additive invitation binding without changing the home tenant`, plus the pre-existing denial-of-unrelated-facility cases), and the real-Postgres run below independently proves it against actual `staff_scope_assignments` rows and RLS.
- `supabase/migrations/20260910130000_facility_invitations_acceptance_tx.sql` — additive migration adding `facility_invitations.department_id`, an append-only `facility_invitation_audit` table, and two `SECURITY DEFINER` Postgres functions (`accept_facility_invitation_existing_user`, `accept_facility_invitation_new_account`) that perform invitation consumption, `staff_scope_assignments` writes, and audit logging as one transaction, with the invitation row locked `FOR UPDATE` for concurrency safety. Not applied to any Supabase project by this task.
- `apps/web/src/lib/platform/facility-invitations.server.ts` rewritten to:
  - separate **existing-user acceptance** (`acceptFacilityInvitationForExistingUser`, requires an already-authenticated session profile whose email matches the invitation; never touches `password_hash`) from **new-account registration** (`registerFacilityInvitationNewAccount`, only reachable when no profile exists for the invited email; hashes the supplied password once, server-side);
  - persist and re-validate the invited `department_id` at acceptance instead of ignoring it;
  - never set `onboarding_complete: true` or any professional-credential field on acceptance; new accounts receive `email_verified_at` because the invitation token proves inbox control, while `verification_status` remains `pending` until the separate approval workflow completes;
  - delegate all success consumption/membership/audit writes to the transactional RPCs above instead of sequential, individually-fallible `update`/`insert` calls. A failed RPC is rolled back by PostgreSQL, so the service boundary records a separate sanitized `ACCEPT_FAILED` event afterward; that distinction is intentional and documented rather than claiming a pre-`RAISE EXCEPTION` row survives.
- `packages/auth/src/mfa-recency.ts` (`hasRecentVerifiedMfa`, `verifyStepUpMfa`) reuses the existing `mfa_enrollments`/TOTP architecture (`packages/auth/src/totp.ts`) while binding assurance to the validated `synapse_sessions.id`; revoked or expired sessions cannot inherit another session's assurance, and the existing auth rate limiter (`apps/web/src/lib/rate-limit.ts`, Upstash-backed with a documented fail-open fallback) gates the step-up route. `packages/auth/src/totp.ts` gained `matchingTotpTimeStep()` so the replay table records the *actual* time-step a code matched (not always "now") — the original version could under- or over-block codes near the edge of the verification window. Replay uniqueness in `mfa_step_up_replays` is keyed globally on `(enrollment_id, time_step)`, not per-session, so a captured code cannot be replayed in a *different* session either. The step-up path handles enrollment-read and assurance-write failures explicitly with distinct error codes.
- `scripts/check-reconciliation-evidence.mjs` — a new, read-only checker for operator-supplied production-migration reconciliation evidence. It fails closed unless the evidence is bound to the current worktree's full HEAD SHA, a checked-in remote-ledger snapshot file (hash-verified), the current local migration hashes (`migration-history.json`), and a reviewed pending-migration set that matches what `check-migration-history.mjs` actually reports as new — and it separately reports `operatorConfirmed` (a human attestation) from `boundEvidenceVerified` (this script's own checks). It never authorizes applying a migration (`productionMigrationAuthorization: "NEVER_GRANTED_BY_THIS_CHECK"`), and its result is surfaced in `readiness-report.mjs` outside the fields that can produce an overall `PASS`.

## Real database test attempt (wave 2, 2026-09-11)

**What was attempted:** replay the full checked-in migration history through `npx supabase start` (the repository's supported local Supabase workflow) to run `facility-invitations.integration.test.ts` against a genuine, disposable Postgres instance.

**Precise blockers found, in order:**

2. After that fix, the chain still cannot be replayed from scratch: `20260609_missing_operational_tables.sql` references `public.pharmacy_customers`, which **no migration in this repository ever creates**. Quarantining that file (and iterating) surfaced a cascade of at least 14 further missing-table/column/function dependencies across pharmacy and early auth-convergence migrations (`pharmacy_products`, `auth_otps`, `role_capabilities`, `current_hospital_id()`, `patient_profiles`, `pharmacy_onboarding`, `subscription_plans.updated_at`, a duplicate RLS policy in `20260716000001_backfill_missing_baseline_tables.sql`, `pharmacy_user_settings`, `pharmacy_product_batches`, and more), none of them related to facility invitations. This is the same pre-existing, already-documented gap described in `docs/readiness/PRODUCTION_MIGRATION_RECONCILIATION_2026.md` (repository migration history does not reproduce the full production ledger). Quarantining files to route around it also removes RLS helper functions this feature's own tests depend on, so it was abandoned rather than pursued further; all quarantined files were restored (verified 81/81 tracked migration files present, `git diff` showing only the two intentional edits below) before continuing.

**What was actually run instead:** a curated, real, disposable Postgres environment — `docker run public.ecr.aws/supabase/postgres:17.6.1.104` (the exact image the Supabase CLI uses; already present locally), bootstrapped with `scripts/db-tests/curated-schema-bootstrap.sql`, which reproduces (verbatim, or with pharmacy/clinical-only columns trivially dropped) only the tables and functions this feature touches: `tenants`, `profiles`, `departments`, `staff_scope_assignments` (with its real unique index and RLS policy), `current_tenant_id()`/`is_platform_admin()`, `mfa_enrollments`, `synapse_sessions`, and the actual `facility_invitations`/`facility_invitation_audit`/`accept_facility_invitation_*` objects from the real, unmodified migration files. This gives real Postgres transactions, real unique constraints, real row locking, and real RLS/grant enforcement (including the genuine `auth.uid()`/`anon`/`authenticated`/`service_role` semantics baked into that exact Supabase Postgres image) — it is not a mock. It does **not** prove the full production schema is reproducible; that remains blocked by (2) above.

**Results:** `scripts/db-tests/run-facility-invitation-db-tests.sh` — **17/17 checks passed**, script exit code 0. Sanitized output (no secrets, only synthetic `*.invalid` emails and placeholder hashes) is committed at `docs/engineering/evidence/facility-invitation-db-test-2026-09-11.log`. Checks covered: the RPC functions execute; department assignment persists; `verification_status` stays `pending` and `onboarding_complete` stays `false` after new-account creation (no premature professional privilege); wrong-recipient rejection (and the invitation remains retryable afterward); existing password unchanged on existing-user acceptance; multi-facility acceptance (a profile with an existing home tenant gains a second, independent facility scope without its home tenant being overwritten); 5-way concurrent redemption of one token yields exactly one winner and exactly one membership row; a genuine mid-transaction failure (forced `profiles` primary-key collision) leaves the invitation `PENDING` with no additional membership row, and a subsequent retry with a fresh id succeeds; and the two `accept_facility_invitation_*` functions' `EXECUTE` grants are verified (via `has_function_privilege()`) to be absent for `anon`/`authenticated` and present for `service_role`.

**A genuine, disclosed infrastructure defect (not a bug in this feature):** this exact Postgres image segfaults the backend (SIGSEGV, followed by automatic crash recovery) whenever *any* role without `EXECUTE` privilege calls *any* `REVOKE`d `SECURITY DEFINER` PL/pgSQL function — reproduced with a trivial, unrelated throwaway function, confirming it is not specific to `accept_facility_invitation_new_account` or a grants mistake (that function already correctly revokes from `public, anon, authenticated`). Because of this, the "anon/authenticated cannot execute the privileged RPC" proof above was obtained by reading the real, persisted grant state with `has_function_privilege()` rather than by invoking the function and expecting a clean "permission denied" — invoking it reliably crashes the backend in this environment. This is disclosed rather than hidden; it does not weaken the actual security posture (the grants are still correctly revoked and independently verified), but it does mean this specific negative-path scenario was proven by grant inspection, not by attempted execution, in this environment.

**Tenant isolation (RLS):** a profile scoped to two facilities saw strictly fewer `staff_scope_assignments` rows than the true (RLS-bypassing) total, and zero rows belonging to an unrelated third profile scoped only to an unrelated tenant — proving the existing `staff_scope_assignments_self_or_admin` policy correctly isolates an unrelated facility's membership data.
